# Research: Named Identities

## R1 Identity method
Decision: one token per person (user, 2026-11-03). Rejected: a display name typed at sign-in
(unverified: anyone can type any name, so the audit trail proves nothing); OIDC (needs an identity
provider, redirect URLs, sessions: far more code and an external dependency for a self-hosted tool).

## R2 Token hash
Decision: SHA-256 of a 256-bit random token. Tokens are high-entropy and generated by the engine,
so a slow password hash (bcrypt/scrypt) adds nothing; SHA-256 is stdlib and fast enough to check on
every request. Comparison: `hmac.compare_digest` against every stored hash (no early exit on name).

## R3 Where people live
Decision: `$AGENTLINE_HOME/people.json`, owner-only, atomic. Rejected: the ledger (schema change in
SQLite and Postgres, Q1/Lane 2 override for no gain: people are engine-local config); the secrets
file (it is `NAME=value` env lines loaded into the process environment, a list of people with flags
does not fit, and hashes are not secrets); `agentline.toml` (forbidden for credentials, even hashed).

## R4 Carrying the identity to the route
Decision: a FastAPI dependency sets `request.state.identity`; routes read it explicitly. Rejected:
a contextvar read by `default_actor()`: sync dependencies and sync endpoints run in separate
threadpool calls with copied contexts, so a value set in the dependency does not reach the endpoint.

## R5 Shared token powers
Decision: the shared token counts as admin (it already can set keys and change pipelines that run
commands; it is also the only bootstrap for engines reached remotely). Its actions are recorded as
`shared-token` so they stand out.
